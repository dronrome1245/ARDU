# ARDU — план реализации атмосферных пресетов «Фон»

**Дата:** 2026-10-08  
**Статус:** ПЛАН ЗАПИСАН В РЕПОЗИТОРИЙ; ЭТАПЫ РЕАЛИЗАЦИИ ЕЩЁ НЕ НАЧАТЫ.  
**Основание:** D-104 и запрос владельца составить и сохранить план; владелец подтвердил, что все hero-фоновые изображения Android его устраивают.  
**Каталог (идея):** [AMBIENT_PRESETS_CONCEPT.md](AMBIENT_PRESETS_CONCEPT.md).  
**Release policy:** [FINALIZATION_PLAN.md](../FINALIZATION_PLAN.md). Настоящий документ **не** меняет scope уже собранной/проверяемой v1 и не разрешает автоматически новую загрузку Nano/ESP.

## 1. Цель и границы

Цель — перейти от четырёх временных Android-макросов поверх F01/F02/F03 к действительно разным атмосферным сценам, которые **локально генерирует Nano** на двух одинаковых кольцах по 44 WS2812B.

**РЕШЕНИЕ (D-104):**
- F01 «Постоянный цвет» остаётся отдельным ручным режимом.
- F02 «Плавная смена цвета» и F03 «Бегущая радуга» исключаются из **будущего пользовательского интерфейса**.
- Уже занятые numeric/wire ID F02/F03 не переиспользовать; текущий firmware/API сохраняется до явной миграции.

**ИДЕЯ, не окончательный scope:** P01…P12 из каталога — **временные номера**, не протокольные ID. Особенно P12 «Радуга» требует отдельного решения: его можно исключить. Состав, характер движения и начальная яркость каждого кандидата утверждаются при просмотре реального света, а не автоматически из таблицы.

**Не меняем:** L01 cold-start, Music/MAX9814/FHT, Night/RTC/Dawn, хлопковый выключатель, режим без роутера ARDU-DIRECT, D6/D7 как зеркальные выходы, общий current limit. Аккумуляторная ветвь отменена (D-100). Никакой новой закупки ради пресетов без отдельного обоснования.

**Обязательная архитектура:** Android → локальный HTTP API ESP8266 → numeric UART → Nano → один буфер 44 LED → D6/D7. ESP и телефон не формируют LED-кадры и не являются хранилищем настроек.

## 2. Проверенный базис и риски (перед кодом перечитать STATUS.md)

- **ФАКТ по ранее пройденной сборке:** Nano v1 flash = 28 024 / 30 720 байт, globals = 1 070 / 2 048 байт. Это **исторический** compile PASS, а не измерение текущего исходника после последних правок.
- Целевые ориентиры FINALIZATION_PLAN: flash ≤95% (=29 184 байт), globals ≤70% (≈1 434 байт) **и** отдельная проверка запаса стека/локальных буферов. От исторического flash до целевого ориентира всего **1 160 байт**; до абсолютного предела **2 696 байт**.
- Наличие памяти для четырёх семейств/12 сцен **не доказано**. Не обещать полный набор до compile/size gate.
- Использовать текущий `04_Прошивка/nano_ardu_v1/nano_ardu_v1.ino` и существующие `ExtendedPersist`, EEPROM-блоки, единый `CRGB leds[44]`; исходную FHT не заменять.
- Для физических испытаний сохранён стендовый current limit **3 000 мА**; hard ceiling в firmware **4 500 мА** не является разрешением поднимать ток без двухкольцевых измерений.
- Финальное потолочное питание — отдельный **Class II 5 В** блок по BOM; S-30-5 с металлическим корпусом и без PE — **только стенд**, не потолочный монтаж.

## 3. Этапы с жёсткими воротами приёмки

### Этап 0 — подготовить контрольную точку (никаких новых прошивок)

**Действия:**
1. Зафиксировать commit SHA известного работающего Nano/ESP/Android, текущий `GET /api/status` и `GET /api/settings`, прошивочные версии, конфигурацию 44 LED, current limit; сохранить отчёты компиляции и recovery-инструкцию.
2. Повторить сборку текущих исходников Nano и ESP в принятом окружении. Записать flash/globals текущего Nano **до** модификаций (не подменять новым измерением исторические 28 024/1 070).
3. Составить карту EEPROM: базовые блоки L01/Clap/Night/Alarm + `ExtendedPersist` от 256, версия, размер, checksum, свободные диапазоны, возможная миграция. Сохранить до экспериментов значения пользователя.
4. Подтвердить с владельцем фактический каталог на будущее, включая P12, и решить отдельно: новый набор входит в следующий **явно санкционированный release** или остаётся задачей после закрытия v1. До такого решения не менять release v1.

**PASS:** получены воспроизводимые baseline build + размер + снимок wire/schema/EEPROM и понятный rollback. **STOP:** baseline не компилируется, нет карты памяти либо не выбран релизный scope.

### Этап 1 — минимальный алгоритмический каркас (без смены API)

**Действия:**
1. Реализовать общий компактный внутренний интерфейс `renderPreset(frame, now, brightness, dynamics)` в изолированной ветке/ревизии, без постоянного изменения numeric UART и EEPROM.
2. Четыре **предлагаемых** семейства рендеринга:
   - градиенты / волны / локальный дрейф;
   - мерцание / огонь / мягкие сгустки;
   - редкие плавно затухающие звёзды;
   - общий цикл дыхания.
3. Использовать уже существующий 44-LED framebuffer, небольшое общее состояние, `millis()` и фиксированную целочисленную математику. Палитры — преимущественно `PROGMEM`; **не** создавать второй 44-LED RGB-буфер, `String` или `delay()`.
4. Для каждого семейства предусмотреть физически ограниченные интенсивность/скорость и отсутствие резких вспышек; соблюдать порядок верхних режимов и обработку UART, FHT, RTC и хлопков.

**PASS:** локальные/CI build и тестовые кадры подтверждают отсутствие переполнений индекса 0..43, блокировок и неожиданной аллокации. Flash/SRAM измерены **после** каждого небольшого коммита. **STOP:** итоговый скетч не помещается либо нарушает текущие режимы.

### Этап 2 — три демонстрационные сцены, а не сразу все 12

| Временное имя | Что должно быть видно на 44 LED | Критерий на реальном кольце |
| --- | --- | --- |
| P01 Северное сияние | Несколько широких зелёно-бирюзово-фиолетовых областей, медленное течение | Цветовые зоны движутся плавно и не превращаются в однотонную заливку |
| P04 Космос | Тёмный сине-фиолетовый фон, редкие независимые мягкие точки | Звёзды появляются/затухают, нет общего мигания всего кольца |
| P05 Камин | Неравномерные тёплые красно-янтарные участки | Живое несинхронное мерцание без стробоскопа |

**Порядок:** сначала статическая проверка кадров/алгоритмов и интегрированная сборка полной прошивки, затем замер memory budget. Физическое испытание проводить **только после** отдельного разрешения на новую полную release-кандидат прошивку согласно FINALIZATION_PLAN (не загружать отдельный standalone-прототип вместо известной рабочей Nano v1).

**PASS:** три заметно разных паттерна, нет случайного перезапуска, UART/RTC/L01/Music/Night regression без изменений, ток в установленном безопасном лимите; владелец принимает внешний вид **на реальной ленте**. **STOP:** memory overflow, сбои подсистем или неразличимые эффекты — оптимизировать один renderer, не добавлять новые сцены.

### Этап 3 — решение о полном каталоге и объёме релиза

По итогам трёх сцен:
1. Совместно зафиксировать окончательные названия, скорость и характер P01…P12 (особенно судьбу P12).
2. Добавлять остальные сцены **малыми группами**, максимально используя общие движки:
   - палитры/волны: P02 Закат, P03 Океан, P07 Лунный свет, P08 Лес;
   - мерцание/сгустки: P06 Свечи, P10 Лава;
   - иное движение градиентов: P09 Неон;
   - дыхание: P11;
   - P12 Радуга — только после отдельного решения.
3. Каждую группу — отдельным коммитом с compile/size + визуальным PASS, не сразу весь каталог.
4. Если полный набор не помещается — сначала общий код, палитры в flash, удаление дублирований, оценка безопасной миграции устаревших F02/F03. **Не удалять legacy wire-команды вслепую**, не предлагать новую плату только из-за нехватки места. Если оптимизация не помогает — согласовать сокращённый каталог или отдельный более поздний релиз.

**PASS:** утверждённый каталог и бюджет памяти; ограничение `≤95% flash, ≤70% globals` — проектный ориентир, дополнительно проверен stack/runtime. **STOP:** нельзя «формально» пройти gate только потому, что компилятор допускает почти полный flash.

### Этап 4 — идентификаторы, сохранение и сквозной контракт

**Начинать только после этапов 2–3:** здесь из предварительного концепта получится контракт, но **сейчас** не назначаем новые номера.

1. Выбрать стабильные preset IDs/диапазон numeric UART, проверить занятые opcode в `06_Интерфейс_управления/UART_V1.md` и сохранить backward compatibility F02/F03 (до отдельной миграции). Обновить `MODEL_IDS.md` только после freeze.
2. Согласовать semantic HTTP: выбор/отключение preset, яркость, динамика, ошибки, активный режим; единый readback в `GET /api/settings` и актуальный `GET /api/status`. Маршрут `POST /api/ambient/preset` — **только кандидат**, не текущий endpoint.
3. В Nano реализовать версионированное EEPROM-хранение выбранной сцены и **независимых** brightness/dynamics каждого пресета. Проверить реальный layout/суммы/границы; миграция старого `ExtendedPersist` сохраняет L01, Music, F01, Night, Alarm, audio calibration, current limit.
4. Live preview — временное изменение в RAM; запись EEPROM только на commit/отпускание слайдера, `EEPROM.update`/эквивалент и проверяемый ACK. Сохранение выбранного preset тоже подтверждается Nano.
5. Системный `reset-defaults` и неизвестная версия EEPROM должны иметь определённое безопасное поведение. После холодного включения всё равно запускается L01; сохранённый Ambient-пресет выбирается при следующем входе в «Фон».

**PASS:** спецификация и тесты схемы; после переподключения/перезапуска значения читаются с Nano, не из Android cache. **STOP:** потеря профилей, нераспознанные версии EEPROM, переполненные команды UART или неоднозначные ID.

### Этап 5 — ESP8266 и Android только на проверенном контракте

1. ESP: обработка нового numeric UART + semantic HTTP + валидация входов, таймауты/ошибки и readback. Одинаковые свойства в Station и `ARDU-DIRECT`. Сам ESP эффект не рендерит.
2. Android: сохранить утверждённый визуальный стиль v0.22 Home Hub и принятые hero-картинки; отдельная карточка F01 «Цвет» + фотокарточки реально реализованных пресетов. Выбор/active highlight — только по подтверждённому state устройства.
3. Для активной сцены показать «Яркость» и «Динамика» («Спокойно ↔ Активно»), для почти статичных — скрыть неприменимое. После повторного входа считывать индивидуальные значения конкретной сцены.
4. Четыре существующих Android-макроса «Северное сияние / Закат / Океан / Космос» не объявлять новой реализацией; удалить/заменить их только вместе с рабочей связкой Nano↔ESP.
5. Убрать F02/F03 **с пользовательского экрана**, когда новые пресеты уже доступны и readback работает. Не переиспользовать старые F02/F03 numeric IDs; legacy wire API удалять лишь при отдельно проверенной миграции.
6. Проверить переходы Light/Music/Ambient/Night/Alarm: при выборе иного раздела текущая декоративная сцена гасится, Alarm остаётся экраном настройки/RTC.

**PASS:** Android build/tests; выбор сцены → HTTP ACK → UART ACK → Nano LED → GET status/settings = выбранной сцене; UI не показывает ложный успех при таймауте.

### Этап 6 — полный физический acceptance и выпуск

**Сначала:** full-source Nano verify/size; затем отдельный ESP build/size + Android tests. Сохранять исходные конфигурации и согласованный rollback. По правилу FINALIZATION_PLAN физические загрузки — **только полными release-кандидатами**, не очередью изолированных тестовых скетчей.

**Сценарии:**
- Одно D6 кольцо: F01 + P01/P04/P05 + остальные утверждённые сцены; каждый пресет физически отличается; проверка изменения яркости/динамики.
- Обе линии D6/D7: 44+44, идентичный кадр, нет дефектов DATA; контроль фактического напряжения/тока/температуры под нагрузкой, текущий лимит 3000 мА до одобрения другого.
- Сквозной путь Android→Wi-Fi→ESP→UART→Nano, readback, reconnect, отсутствие домашнего роутера (`ARDU-DIRECT`).
- Переходы Music↔Ambient↔Night↔Light, FHT/MAX9814/хлопок, Night schedule, RTC/Alarm/Dawn, `reset-defaults`.
- EEPROM: поменять параметры двух разных сцен и F01, сохранить, полностью выключить питание второй клавишей, включить; **L01 стартует**, а ранее сохранённые сцены восстанавливают свои параметры при выборе.
- Нестандартные настройки старого v1 после миграции не теряются; неизвестные команды/ошибки связи не повреждают state.

**PASS:** матрица испытаний с результатами, actual Flash/SRAM и измерения владельца на железе, firmware/App версии и commit SHA зафиксированы в STATUS/HISTORY. **FAIL:** восстановить сохранённый проверенный release и диагностировать только нарушенный gate. Не объявлять релиз завершённым по CI без физического smoke.
