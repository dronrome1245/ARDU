# NIGHT D-125 — аппаратная приёмка через Wi-Fi (Nano R6)

Дата: 2026-11-07  
Статус: **R6 записана и побайтово проверена на Nano (2026-11-07)**; ESP R3 `write 29378 B → verify 29378 B → /api/status PASS`. **Функциональная приёмка семантики Night D-125 на устройстве ещё НЕ PASS**.

## Что должно работать

1. При `schedule_enabled=true` событие ON выбирает NIGHT (за исключением активного DAWN).
2. Вручную NIGHT включается в любое время, даже вне окна расписания.
3. Ручной LIGHT / AMBIENT / MUSIC / OFF после ON не перебивается до следующей границы ON.
4. OFF по расписанию выключает только если в этот момент включён NIGHT.
5. При холодной подаче питания или сбросе внутри окна NIGHT включается сразу; вне окна действует обычная startup-логика.
6. При `schedule_enabled=false` плановых переходов нет.
7. Рассвет имеет приоритет; при отключённом питании Nano автономный таймер ночника не работает.

Код: `04_Прошивка/nano_warm_dawn_v6/nano_warm_dawn_v6.ino` (boot `ARDU1 7`); API, UART v1 и Android менять не требуется. Подтверждение исходника/CI не означает успешную физическую запись.

## Перед тестом

- Не писать Nano повторно вслепую: прошлая R6 запись через ESP R2 доходила до 100%, но byte-for-byte verify многократно FAIL.
- Установить на ESP **R3 DIAG** через существующий ArduinoOTA; локально заполнить Wi-Fi/OTA пароли, не коммитить их. Убедиться, что `http://192.168.0.4/api/ping` возвращает `fw:ARDU_ESP_V4_NANO_REMOTE_R3_DIAG` и `nano_remote_flash:true`. Если адрес ARDU изменился — подставить актуальный.
- Подготовить HEX **ровно** из исходника `nano_warm_dawn_v6`: в Arduino IDE выбрать Nano / ATmega328P (Old Bootloader), выполнить **Sketch → Export Compiled Binary**; нужен файл `nano_warm_dawn_v6.ino.hex`. Не использовать `*.with_bootloader.hex`.
- Все подключения RESET GPIO4/BC548 из `02_Архитектура_и_решения/NANO_REMOTE_FLASH.md` уже должны быть физически проверены. Не подключать Nano USB и не выключать питание во время сеанса.
- Выключить будильник на время функциональных испытаний ночника, если его срабатывание помешает тесту; после испытаний вернуть пользовательские настройки. Проверить `rtc_valid:true`.

## 1. Безопасный первый gate — только verify, запись запрещена

В PowerShell из `C:\ARDU`:

```powershell
git pull
.\tools\flash_nano_over_wifi.ps1 `
  -HexPath ".\04_Прошивка\nano_warm_dawn_v6\nano_warm_dawn_v6.ino.hex" `
  -DeviceIp 192.168.0.4 -VerifyOnly
```

Скрипт сам запрашивает текущий OTA-пароль ESP. `-VerifyOnly` запускает `avrdude -U flash:v:<hex>:i` (с аппаратным reset Nano), **не отправляет flash:w** и затем печатает `/api/system/nano-program/status`. Нужны:

- `AVRDUDE` exit code 0 / verified;
- `uart_overrun=false`, `uart_rx_error=false`; максимальные очереди и byte counters сохранять для диагностики;
- восстановление `GET /api/status` с `ok:true` и `rtc_valid:true`.

Если verify FAILED — сохранить весь лог и диагностику и **не выполнять режим записи** до выяснения причины. Старт `ARDU1 7` не заменяет verify.

Если текущий HEX не совпадает с прошитым, зафиксировать расхождение. Запись допускается только после того, как транспорт получит надёжный полный verify, иначе рискуем повредить работающее устройство.

## 2. Сценарии D-125 на устройстве

Через Android-приложение (или `/api/night/settings`, `/api/mode`) проверить по очереди; перед каждым испытанием читать `/api/time` и `/api/status`:

1. **Ручной NIGHT днём.** Вне расписания выбрать Ночник; убедиться в свете и `mode=night`. Отключить вручную — `mode=off`.
2. **Автоматический ON.** Установить время ON через 2–3 минуты и OFF ещё через 2–3 минуты (интервал может пересекать полночь). Включить расписание. На границе ON — `mode=night`.
3. **Ручной override.** После авто-ON выбрать LIGHT. До OFF должен оставаться `mode=light`; после OFF — тоже `mode=light`, свет не выключается.
4. **Выключение NIGHT по границе OFF.** В следующем цикле дать ON выбрать NIGHT, не менять режим; по OFF получить `mode=off`.
5. **Перезапуск внутри окна.** При RTC внутри установленного интервала краткий reset Nano (без потери питания ESP) должен привести к NIGHT, если нет восстанавливаемого DAWN. Холодную подачу питания проверять отдельно и безопасно, не при активной записи/verify.
6. **Без расписания.** Отключить schedule, вручную включить NIGHT вне интервала; режим должен оставаться NIGHT и не отключаться по старой границе.
7. **Приоритет DAWN.** При активном рассвете событие ON не должно переключать устройство на NIGHT.

Вернуть изначальные настройки Night и Alarm после теста. Для всех автоматических проверок Nano должна оставаться под питанием, часы DS3231 должны быть валидны.

## Критерий закрытия

`R6 HEX совпал при полном verify` + `/api/status` восстановился + сценарии 1–7 воспроизводимы → отметить D-125 **hardware PASS** в STATUS/HISTORY.

Отдельный критерий качества механизма будущих Wi-Fi обновлений — полный **write + verify + /api/status** на новой ревизии через R3 или выше. Проверка без записи доказывает только корректность текущего содержимого и пути чтения, не доказывает надёжность будущего write.

Это **не** доказательство порчи Flash и **не** доказательство идентичности с текущим исходником. Не повторять запись вслепую. После ошибки скрипт ещё не подтвердил работоспособность приложения: `GET /api/status`, `/api/time`, `/api/settings` выполнить отдельно. ## 2026-11-07 — подтверждённая установка R6 по Wi-Fi

Владелец выполнил реальную запись **без** `-VerifyOnly` через R3 DIAG, AVRDUDE 8.0: `Writing 100% 13.92 s`, `Reading 100% 12.47 s`, **`29378 bytes of flash verified`**. Диагностика моста: `uart_overrun=false`, `uart_rx_error=false`, `last_result=disconnected`, RX=512, TCP→UART=33648, UART→TCP=31450, max TCP=133, max UART=102. `/api/status` после возвращения обычного UART — `mode=light`, `rtc_valid=true`, `current_limit_ma=3000`, `ok=true`. **Gate Wi-Fi upload write+verify+post-status = PASS**; источник `nano_warm_dawn_v6` доставлен побайтово. Исторический verify-only mismatch до записи больше не является актуальной ошибкой установленной версии. **Gate функциональности D-125** (ручной Night вне окна, расписание, ручное переопределение, DAWN, restart) пока открыт; не объявлять его PASS без физического или API-проверенного сценария.
