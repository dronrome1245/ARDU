# Статус проекта ARDU

Дата состояния: 2026-09-20

## Текущий этап

**Этап 3 — функциональная модель режимов и нового Wi‑Fi приложения определена; выполняются электрические измерения, далее нужны физическая схема двух корпусов и первый стенд ESP8266 ↔ Nano.**

## Что подтверждено и решено

- Два старых круглых плоских светильника используются только как корпуса под WS2812B: светомузыка, фоновые эффекты, ночник и световой будильник.
- Основной белый свет комнаты — отдельные точечные светильники на первой клавише.
- Вторая клавиша полностью снимает питание ARDU. Будильник сработает только если эта клавиша оставлена включённой; повседневное выключение света выполняется программно.
- Два корпуса работают синхронно от одного Nano/ESP8266/MAX9814/DS3231.
- Рабочая архитектура: `приложение → домашний Wi‑Fi → ESP8266 → UART → Nano → два кольца WS2812B + MAX9814 + DS3231`.
- Wi‑Fi: Station основной, SoftAP резерв. Облако не требуется.
- В наличии 5 м WS2812B; для двух колец нужно около 1,43 м.
- Плотность фактической ленты ≈60,7 LED/м. Для кантика 71,5 см цель — 43 LED на корпус, 86 суммарно, с физической проверкой до резки.
- БП S-30-5 5 В 6 А остаётся базовым; на выходе фактического экземпляра измерено `5,01 В` без существенной нагрузки, проверка под нагрузкой ещё требуется; программный лимит лент ориентировочно 4,5 А до фактической проверки.
- DATA: D6 → кольцо A, D7 → кольцо B; одинаковый кадр на оба кольца.
- Предварительная распиновка Nano: D0/D1 UART ESP8266, A0 MAX9814, A4/A5 DS3231.
- Белая переходная плата ESP8266 питается только 3,3 В; 5 В на VCC запрещены.
- YP-8/AMS1117-3.3: при диагностике 2026-09-20 с общим чёрным щупом на `S-30-5 V-` измерено: `S-30-5 V+ ≈ 5,0 В`, `YP-8 VIN+ ≈ 4,7 В`, `YP-8 VOUT+ ≈ 3,50 В`, `ESP VCC ≈ 3,25 В`. Эти значения относятся к общей точке `S-30-5 V-` и сами по себе не дают истинное напряжение YP-8/ESP между локальными `VCC/GND`; вероятно есть заметное падение по GND-проводнику. Питание ESP считать **неподтверждённым для Wi‑Fi** до измерения `YP-8 GND` и `ESP GND` относительно `S-30-5 V-` и пересборки контактов.
- Nano как USB↔UART-мост: loopback-тест 2026-09-19 пройден (`RESET→GND`, `D0/RX↔D1/TX`). По новым крупным фото 2026-09-20 **штатный последовательный `1 кОм` именно на нашем экземпляре не подтверждён**: рядом с USB-UART видны два SMD `151` (=150 Ом), а четыре `102` (=1 кОм) расположены у индикаторов RX/TX/POW/L. Точный резистор в пути USB-UART→D0 нужно установить измерением конкретной платы.
- Внешний делитель `1,5 кОм / 3,0 кОм` фактически дал `Nano D0 = 4,95 В`, `ESP RX = 3,36 В`. Эти измерения сами по себе хорошо согласуются с расчётом внешнего делителя и **не подтверждают наличие дополнительного 1 кОм перед D0**. До изменения programmer-path сначала измерить, связан ли D0 с парой `151` и какое сопротивление реально стоит между USB-UART и D0.
- Первый тестовый скетч ESP8266 успешно компилируется в Arduino IDE. Отчёт сборки: RAM `28108/80192` (35%), IRAM `59747/65536` (91%, включая 32768 байт cache), код во flash `236148/1048576` (22%).
- **Прошивка ESP8266 воспроизводимо проходит на 100%** через Nano USB↔UART при `Upload Speed = 115200`, установленном локальном `100 µF 10 V`, временном прямом `Nano D0 → ESP RX`, `GPIO0 = LOW` и ручном кратком reset `RST ESP → GND` во время `Connecting...`. После обычного boot тестовый скетч выводит `ARDU ESP8266 OK`. Это подтверждает ESP8266, flash и USB↔UART-мост. Прямой путь `D0 ≈ 4,95 В → ESP RX` остаётся только диагностическим и **не допускается как штатная схема**.
- DS3231 имеет цепь подзаряда; с установленной CR2032 проектное решение — отключить зарядную цепь (удалить резистор `201`).
- Предыдущий MIT App Inventor проект `Ardublock2.aia` (`LumpV3.1`) полностью разобран как функциональный источник.
- В старом приложении подтверждены 9 ColorMusic-режимов, подрежимы, общие яркости, калибровка, будильник и незавершённые разделы ночника/фона.
- Старый Bluetooth-протокол больше не считается обязательным контрактом. Новый внешний интерфейс — локальный HTTP API; внутренний ESP8266↔Nano протокол будет компактным UART.
- Созданы целевые документы по режимам, приложению, API и разбору старого `.aia`.

## Следующий практический шаг

1. По явному решению владельца диагностику programmer-divider временно отложить; прямой ~5 В `D0→ESP RX` не считать штатно разрешённым соединением.
2. `FW-0` Nano **пройден**: на Mini-USB Nano требуется `ATmega328P (Old Bootloader)`; `PING→PONG` и `STATUS` работают.
3. Перейти к `FW-1`. Код подготовлен: `04_Прошивка/nano_fw1/nano_fw1.ino`.
4. Сначала только скомпилировать FW-1 и подтвердить наличие библиотеки FastLED; физическое кольцо пока не подключать.
5. После успешной компиляции собрать один WS2812B-стенд на D6 с ограничением 500 мА и проверить F01.

## Следующая контрольная точка

**Питание измерено, потолочная разводка определена, окончательный BOM утверждён, ESP8266 прошивается и устойчиво обменивается командами с Nano; одно кольцо управляется по Wi‑Fi.**


### Диагностика programmer UART 2026-09-20

- Повторная безопасная попытка с делителем `1,5 кОм / 3,0 кОм` при оставленном `100 µF 10 V` снова завершилась ошибкой загрузки. Точный код ошибки в этом сообщении не зафиксирован.
- Поскольку без делителя + 100 µF полная прошивка на 115200 прошла успешно, а возврат делителя снова нарушил upload, высокий импеданс/качество programmer UART остаётся подтверждённым подозреваемым фактором.
- Следующий тест: низкоомный делитель `750 Ом / 1,5 кОм` из имеющихся резисторов 1,5 кОм, с обязательным измерением HIGH до подключения ESP.


### Вход в ROM bootloader ESP8266 2026-09-20

- При Upload Speed `57600` без ручного reset esptool остаётся на `Connecting...` и соединение не устанавливается.
- Если при `GPIO0 = LOW` кратковременно замкнуть `RST ESP → GND` и отпустить, загрузка начинается.
- Это подтверждает: для текущего стенда Nano-as-USB↔UART автоматический reset/boot ESP не реализован; вход в ROM bootloader выполняется вручную.
- Ошибка отсутствия connect и возможные ошибки уже во время записи — разные этапы диагностики.


### Повторяемость прошивки ESP8266 2026-09-20

- Полная запись на `115200` без внешнего делителя повторно подтверждена: upload доходит до `100%` при ручном кратком reset `RST→GND` на этапе `Connecting...`.
- Без ручного reset соединение с ROM bootloader не начинается.
- С делителем `1,5 кОм / 3,0 кОм` upload снова завершается ошибкой.
- Прямой 5-вольтовый TX не использовать дальше как рабочую схему; задача теперь — сохранить эту устойчивость при безопасном уровне RX.


### Переход к FW-0 Nano 2026-09-20

- Владелец решил временно не тратить время на дальнейший подбор programmer-divider, пока диагностическая прошивка ESP воспроизводимо работает.
- Это **не** отменяет ограничение по уровню: прямой ~5 В на ESP RX остаётся небезопасным и не принимается как финальная схема.
- Создан первый кодовый слой `04_Прошивка/nano_fw0/nano_fw0.ino`: неблокирующий Serial parser, команды `PING`, `STATUS`, `HELP`, централизованные пины D6/D7/A0/A4/A5 и безопасный LOW на DATA-кольцах при старте.
- Код ещё не проверен компиляцией/загрузкой на физической Nano; следующий критерий — аппаратный тест владельца.


### Первая аппаратная попытка FW-0 Nano 2026-09-20

- `nano_fw0.ino` успешно компилируется для выбранной Nano: flash `2514 / 30720` байт (8%), SRAM `254 / 2048` байт (12%).
- Загрузка в Nano не завершилась: 10 попыток `not in sync: resp=0x41`, затем `unable to open port COM3 for programmer arduino`.
- `0x41` соответствует ASCII `A`; с учётом ранее работающего ESP-скетча `ARDU ESP8266 OK` первым проверяется остаточное подключение ESP к D0/D1 Nano. Это пока диагностическая гипотеза, не факт.
- Следующий тест: полностью отключить ESP от D0/D1, убрать `RESET Nano→GND`, закрыть Serial Monitor и повторить upload без изменения Processor/bootloader.


### FW-0 Nano: ESP исключён из причины `resp=0x41`

- Повторный Upload выполнен при полностью отключённых от Nano линиях D0/D1, снятой перемычке `RESET→GND` и закрытом Serial Monitor.
- Результат не изменился: `not in sync: resp=0x41`.
- Следовательно, гипотеза о помехе от ESP8266 на UART Nano для этой ошибки исключена.
- Следующий тест: выбрать `ATmega328P (Old Bootloader)` и повторить Upload на той же Nano/COM3.

### FW-1: схема WS2812B приведена к рекомендациям AlexGyver 2026-09-20

- По явному решению владельца для узлов, у которых есть проверенная схема исходного проекта ColorMusic/AlexGyver, использовать её как базовую и отклоняться только по отдельной инженерной причине.
- Для WS2812B официальная страница ColorMusic рекомендует электролит по питанию ленты минимум `1000 µF`, напряжение не ниже `6,3 V`; общий WS2812-гайд AlexGyver рекомендует `1000–2200 µF` на питание ленты.
- DATA-резистор — отдельный элемент: в WS2812-гайде AlexGyver рекомендованы `200–500 Ом`. Конденсатор 1000 µF не является заменой DATA-резистора.
- Предыдущая временная рекомендация использовать `1,5 кОм` в DATA для FW-1 отменена.
- До физического FW-1 нужно подтвердить номинал/напряжение имеющегося `1000 µF` и наличие резистора `200–500 Ом` (предпочтительно 330 Ом).


### Конденсатор 1000 µF для WS2812B подтверждён

- Фактический электролит для входа питания ленты имеет маркировку `1000 µF 6.3 V`.
- Для 5-вольтовой линии он подходит и соответствует минимальному рабочему напряжению, указанному в рекомендациях ColorMusic/AlexGyver.
- Следующий аппаратный блокер FW-1 — DATA-резистор в диапазоне `200–500 Ом` (предпочтительно 330 Ом).


### FW-1: DATA-резистор подтверждён

- Владелец подготовил последовательный резистор `220 Ом` для DATA WS2812B.
- Номинал входит в диапазон `200–500 Ом`, принятый по рекомендациям AlexGyver.
- Для физического FW-1 теперь подтверждены оба пассивных элемента: `220 Ом` в DATA и `1000 µF 6,3 V` параллельно питанию ленты.
- Следующий шаг — загрузить `nano_fw1.ino` в Nano без подключённой ленты, затем собрать один канал D6→220 Ом→DIN и проверить F01 на первых 43 LED.

### Решение по второму каналу после FW-1

- Владелец решил не переходить сейчас к физическому FW-2.
- Канал `D7` остаётся зарезервирован под второе кольцо и должен в дальнейшем **зеркально повторять кадр D6**, без отдельного режима/состояния.
- Физическое подключение и тест второго кольца откладываются до полной настройки и стабилизации первого кольца.
- Подготовленный `nano_fw2` сохраняется как черновик будущей проверки двух выходов, но не является текущим следующим шагом.
- Текущий фокус: довести одно кольцо до полного рабочего контура. Ближайшая проверка — завершить управление F01 (`OFF/ON/BRIGHT/COLOR`), затем переходить к следующему подсистемному слою на том же кольце.


### F01 одного кольца полностью проверен; следующий слой MAX9814

- Команды `OFF`, `ON`, `BRIGHT 8`, `BRIGHT 64`, `STATUS` проверены владельцем на физическом D6-кольце и работают.
- F01/управление одним кольцом считаются полностью закрытыми для текущего этапа.
- Согласно актуальному однокольцевому порядку следующий слой — MAX9814 на A0.
- Подготовлен `04_Прошивка/nano_mic_test/nano_mic_test.ino`: сохраняет F01 и добавляет неблокирующую диагностику микрофона командой `MIC` (`AVG/MIN/MAX/P2P`).
- Базовая схема MAX9814 берётся по AlexGyver: `Vdd→5V`, `GND→GND`, `Out→A0`; `Gain` и `AR` на первом тесте оставить неподключёнными. Внешний AREF пока не используется, чтобы не добавлять второй неизвестный узел.


### Первые измерения MAX9814 на A0

- Получены два диагностических окна по 50 мс: `AVG=249 MIN=61 MAX=413 P2P=352 SAMPLES=251` и `AVG=252 MIN=130 MAX=415 P2P=285 SAMPLES=251`.
- Среднее около 250 ADC хорошо соответствует ожидаемому смещению выхода MAX9814 около 1,25 В при стандартном 5-вольтовом ADC Nano (идеально около 256 отсчётов).
- В обоих окнах нет явного клиппинга в 0/1023, но P2P уже велик (`285–352`). По этим двум строкам нельзя надёжно сравнить тишину и хлопок: команда `MIC` показывает только последнее завершённое 50-мс окно и может не захватить короткий импульс.
- В `nano_mic_test.ino` добавлена команда `MIC1S`: после запуска она собирает непрерывное 1-секундное окно и автоматически печатает AVG/MIN/MAX/P2P/SAMPLES. Следующий тест — одно окно `MIC1S` в тишине и одно с хлопком/речью в течение самой секунды захвата.


### MAX9814: реакция на звук подтверждена, 60 dB перегружает вход на громком сигнале

- `MIC1S` в тишине: `AVG=252 MIN=108 MAX=417 P2P=309 SAMPLES=4998`.
- `MIC1S` при громком звуке/хлопке: `AVG=307 MIN=0 MAX=886 P2P=886 SAMPLES=4995`.
- Микрофон и A0 однозначно реагируют на звук: P2P вырос с 309 до 886.
- При громком тесте MIN достиг `0`, то есть отрицательная полуволна упёрлась в нижнюю границу ADC; текущий `Gain` floating = 60 dB слишком высокий для громкого сигнала.
- Следующий минимальный тест: соединить `Gain MAX9814 → GND` (50 dB), оставить `AR` неподключённым, повторить `MIC1S` в тишине и при громком звуке. Внешний AREF сейчас не применять: уменьшение опоры ADC только уменьшит запас до клиппинга.


### MAX9814: попытка Gain→GND дала ненормальный нулевой выход

- После изменения только `Gain→GND` получено: `MIC1S AVG=0 MIN=0 MAX=5 P2P=5` и `AVG=0 MIN=0 MAX=16 P2P=16`.
- Это **не соответствует** ожидаемому поведению MAX9814 при 50 dB: DC-смещение OUT должно сохраниться, а не падать почти до нуля.
- Поскольку до перемычки модуль выдавал `AVG≈252`, первым подозревается ошибка подключения/замыкание OUT или неверный контакт Gain, а не внезапная неисправность микрофона.
- Следующий минимальный тест: обесточить стенд, полностью снять перемычку Gain→GND и вернуть точную предыдущую схему `Vdd→5V`, `GND→GND`, `Out→A0`, `Gain/AR` свободны; после включения повторить `MIC1S`. Если AVG снова около 250 — модуль исправен, затем отдельно идентифицировать физический пин Gain перед повтором.


### MAX9814: после снятия Gain→GND рабочий выход восстановился

- После снятия перемычки `Gain→GND` и возврата `Gain` в floating при шуме получено `MIC1S AVG=278 MIN=0 MAX=508 P2P=508 SAMPLES=4996`.
- Это подтверждает, что MAX9814 и вход A0 снова работают; предыдущий почти нулевой результат был связан именно с подключением перемычки/контактом, а не с окончательной неисправностью модуля.
- При floating Gain=60 dB сигнал всё ещё достигает нижней границы ADC (`MIN=0`), поэтому 60 dB для громкого сигнала избыточны.
- До повторной попытки 50/40 dB нужно физически перепроверить, что перемычка ставится именно на вывод `Gain`, а не на соседний `Out`/другую дорожку. Лучше подтвердить фото/маркировкой платы.


### MAX9814: по фото подтверждена распиновка конкретной платы

- На крупном фото читается порядок выводов слева направо: `AR`, `Out`, `Gain`, `Vdd`, `GND`.
- В текущем рабочем подключении: `Out` — жёлтый провод, `Vdd` — зелёный, `GND` — синий; `AR` и центральный `Gain` свободны.
- Для режима 50 dB нужно соединить именно центральный свободный вывод `Gain` с крайним правым `GND`; `Out` (жёлтый) остаётся подключён к A0, `AR` остаётся свободным.
- Перед повтором теста рекомендуется проверить, что перемычка не касается `Out`.


### MAX9814: 50 dB подтверждён, но громкий сигнал всё ещё клиппует

- При `Gain→GND` (50 dB) тишина: `AVG=250 MIN=85 MAX=360 P2P=275 SAMPLES=5000`.
- При громком звуке: `AVG=260 MIN=0 MAX=507 P2P=507 SAMPLES=996`.
- DC-смещение снова нормальное (`AVG≈250`), значит теперь `Gain→GND` подключён правильно.
- На громком сигнале `MIN=0`: нижний клиппинг сохраняется даже при 50 dB. Следующий штатный режим платы — `Gain→Vdd` (40 dB).
- Второй capture имеет аномально низкое число выборок (`996` вместо ~5000/с); это не меняет вывода о клиппинге, но после перехода на 40 dB нужно проверить, повторяется ли аномалия.


### MAX9814 на 50 dB: шум от ленты не выявлен, клиппинг остаётся

- При `Gain→GND` (50 dB) в спокойном состоянии получено `AVG=250 MIN=85 MAX=360 P2P=275 SAMPLES=5000`.
- При шуме с включённой лентой: `AVG=260 MIN=0 MAX=507 P2P=507`; при шуме без ленты: `AVG=257 MIN=0 MAX=506 P2P=506`.
- Практически одинаковые MIN/MAX/P2P при шуме с лентой и без неё показывают, что в текущем стенде WS2812B не вносит заметной дополнительной помехи в A0.
- Но при громком сигнале `MIN=0` сохраняется, то есть 50 dB всё ещё даёт клиппинг по нижней границе ADC.
- Следующий минимальный тест — `Gain→Vdd` (40 dB), `AR` оставить floating, повторить тишину и громкий звук. Если клиппинг исчезнет и P2P останется уверенно выше тихого уровня, 40 dB принять рабочим Gain для M01.


### MAX9814 на 40 dB: FW-4 закрыт, начат M01

- `Gain→Vdd` (40 dB), тихое окно: `AVG=250 MIN=205 MAX=282 P2P=77 SAMPLES=4997`.
- Громкий звук/хлопок: `AVG=250 MIN=0 MAX=503 P2P=503 SAMPLES=4999`.
- На 40 dB тихий фон резко уменьшился по сравнению с 50/60 dB, а реакция на звук остаётся сильной. Краткий экстремальный хлопок всё ещё достигает нижнего rail (`MIN=0`).
- Для M01 это не блокирует продолжение: исходный ColorMusic v2.10 в VU-режимах использует максимум положительных отсчётов, порог тишины, экспоненту 1.4, сглаживание 0.3 и медленный автогейн. Наш положительный максимум меняется примерно от `282` в тишине до `503` при громком звуке.
- Критерий FW-4 выполнен: уровень звука устойчиво отличается от шума помещения. Рабочее состояние MAX9814 для M01 — `Gain→Vdd` (40 dB), `AR` floating.
- Создан `04_Прошивка/nano_m01/nano_m01.ino`, адаптирующий VU-логику ColorMusic под одно кольцо 43 LED на D6. Добавлена команда `CAL`, которая измеряет тихий максимум и ставит `LOW_PASS = quietMax + 13`, как в ColorMusic.

### FHT library choice

- В Arduino Library Manager доступна `AvrFHT` (KobaProduction), но текущий тестовый код ARDU использует API исходной `FHT.h`, как ColorMusic v2.10.
- `AvrFHT` является переработкой старой ArduinoFHT/OpenMusicLabs и меняет структуру заголовков; она не считается drop-in заменой для текущего скетча без адаптации.
- По решению проекта придерживаться проверенной сборки AlexGyver для FHT-этапа используем точную библиотеку `libraries/FHT` из официального репозитория `AlexGyver/ColorMusic` и устанавливаем её вручную в Arduino libraries.


### FHT dependency: переходим на AvrFHT

- Проверен `KobaProduction/AvrFHT` версии `1.1.1`: библиотека предназначена для AVR и является модернизированной версией старой ArduinoFHT/Open Music Labs.
- Она подходит для Arduino Nano ATmega328P, но API немного отличается от старой FHT: используется `FHT_SAMPLES_N`, модульные headers и `fht_transform()` вместо `fht_run()`.
- У AlexGyver FHT действительно есть: в официальном репозитории ColorMusic лежит `libraries/FHT/FHT.h` и связанные таблицы. Это старая библиотека, вложенная в проект, поэтому она может не появляться как отдельная библиотека в Library Manager.
- `04_Прошивка/nano_fht_test/nano_fht_test.ino` переведён на AvrFHT. Для MAX9814 дополнительно введено программное вычитание измеренного DC offset перед FHT; ADC reference остаётся DEFAULT.


### AvrFHT: первая CALF выявила неверное измерение DC, тест исправлен

- Первая попытка после перехода на AvrFHT дала `CALF DC=914 QUIET_MAX=32 SPECTR_LOW_PASS=35`, после чего `FREQ` в тишине и при музыке возвращал нули.
- `DC=914` резко противоречит ранее многократно измеренному MAX9814 offset около `250` ADC, поэтому эти FHT-результаты считаются недействительными.
- Наиболее вероятная причина — измерение DC offset после переключения ADC на быстрый prescaler=32. Код исправлен: DC и отдельная команда `ADC` теперь измеряются на штатном prescaler=128, первые преобразования после переключения отбрасываются, затем для FHT возвращается prescaler=32.
- Следующий тест: загрузить обновлённый `nano_fht_test.ino`, сначала выполнить `ADC`. Ожидаемый AVG около 250. Только затем `CALF`, `FREQRAW`, `FREQ`.


### AvrFHT: повтор CALF всё ещё даёт аномальный DC≈946

- Повтор после исправления: `CALF DC=946 QUIET_MAX=33 SPECTR_LOW_PASS=36`.
- `FREQRAW`: `LOW=19 MID=27 HIGH=19 PEAK=27` и затем `LOW=19 MID=19 HIGH=19 PEAK=19`.
- DC≈946 по-прежнему противоречит ранее подтверждённому MAX9814 offset≈250 на том же A0, поэтому частотные результаты пока не использовать для принятия решений.
- Ключевой следующий тест уже есть в свежем скетче: команда `ADC`. Она одновременно проверяет физический A0 и подтверждает, что на Nano действительно загружена последняя версия скетча (в старой версии команда отсутствует).
