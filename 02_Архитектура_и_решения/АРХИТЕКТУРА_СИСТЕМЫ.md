# Архитектура системы

## 1. Контекст

Проект объединяет три разные по характеру задачи:

1. обработка аудиосигнала и анимация LED в реальном времени;
2. сетевое управление со смартфона;
3. часы и сценарий рассвета.

Чтобы не переносить сразу весь существующий AVR-код на ESP8266, задачи разделяются между Nano и ESP8266.

## 2. Логическая схема

```text
┌─────────────────────┐
│ Мобильное приложение│
└──────────┬──────────┘
           │ Wi‑Fi
           ▼
┌─────────────────────┐
│ ESP8266MOD           │
│ Wi‑Fi gateway        │
│ TCP / сетевой слой   │
└──────────┬──────────┘
           │ UART, строки + \n
           ▼
┌─────────────────────┐
│ Arduino Nano         │
│ state machine        │
│ audio / RTC / LEDs   │
└──────┬───────┬──────┘
       │       │
       │       ├────────────► DS3231
       │
       ├────────────────────► WS2812B
       │
       └────────────────────► MAX9814
```

## 3. Ответственность ESP8266

ESP8266 должен быть максимально тонким шлюзом.

Обязанности:

- поднять Wi‑Fi;
- принять соединение приложения;
- читать строки до `\n`;
- проверять максимальную допустимую длину строки;
- передавать допустимую строку Nano;
- читать ответы Nano;
- отправлять их обратно приложению;
- восстанавливать сетевое соединение без перезапуска Nano.

ESP8266 не должен в первой версии:

- анализировать микрофон;
- рассчитывать FHT;
- хранить истинное состояние лампы;
- самостоятельно выполнять музыкальные эффекты.

## 4. Ответственность Arduino Nano

Nano — единственный владелец состояния лампы.

Он должен:

- разбирать команды;
- выбирать активный режим;
- читать MAX9814;
- выполнять VU/частотные алгоритмы;
- управлять WS2812B;
- вести RTC;
- выполнять рассвет;
- хранить пользовательские настройки;
- возвращать статусы/ошибки.

## 5. Командный интерфейс

Принцип:

`transport-independent commands`.

Одна и та же строка должна означать одно и то же независимо от того, пришла она:

- от HC-05;
- от ESP8266;
- из аппаратного Serial при отладке.

Таким образом, миграция Bluetooth → Wi‑Fi не требует переписывания бизнес-логики.

## 6. Wi‑Fi

ESP8266 поддерживает Wi‑Fi и может использоваться в проекте без ESP32.

Режим сети пока не зафиксирован:

- SoftAP — телефон подключается непосредственно к лампе;
- Station — лампа подключается к существующей Wi‑Fi сети.

Выбор фиксируется после стендового теста и оценки удобства мобильного приложения.

## 7. UART и логические уровни

ESP8266 работает с 3.3-вольтовой логикой. Nano обычно работает с 5-вольтовой логикой.

Поэтому линия `Nano TX → ESP8266 RX` требует согласования уровня, если конкретная переходная плата не содержит подтвержденной схемы согласования.

Линию питания ESP8266 нельзя определять по одному внешнему виду платы. До подключения нужно подтвердить, какое напряжение допускается на контакте `VCC` конкретной переходной платы.

## 8. Аудиотракт

MAX9814 остается на стороне Nano.

Это позволяет:

- использовать накопленные тесты;
- избежать неопределенности по диапазону ADC ESP8266;
- не переписывать сразу AVR-ориентированный анализ;
- отделить сетевые задержки от аудиосэмплирования.

## 9. Машина состояний

Основные состояния:

```text
OFF
NORMAL_LIGHT
NIGHT_LIGHT
MUSIC
EFFECTS
ALARM_DAWN
```

`ALARM_DAWN` имеет высший временный приоритет.

После завершения/остановки рассвета система должна вернуться в заранее определенное пользовательское состояние. Конкретное правило возврата фиксируется при реализации будильника.

## 10. Отказоустойчивость

При потере Wi‑Fi:

- текущий режим Nano продолжает работать;
- LED-анимация не должна зависать;
- RTC продолжает работать;
- ESP8266 пытается восстановить связь независимо.

При перезапуске ESP8266 Nano не должен перезапускаться.

## 11. Путь эволюции

Если позже появится ESP32, проект можно упростить до одного MCU, но это отдельная миграция. Текущая архитектура специально не требует такой покупки.
