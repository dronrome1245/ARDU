# Правила ведения проекта ARDU

## 1. Обязательный вход для любой нейросети

Проект ведётся из разных чатов и может продолжаться другой нейросетью.

Перед работой читать:

1. `00_AI_START_HERE.md`;
2. `STATUS.md` — единственный канонический текущий статус;
3. `DECISIONS.md` — решения и их замены;
4. `HISTORY.md` — фактически выполненное;
5. `SOURCES.md` — внешние и пользовательские источники;
6. этот файл;
7. `02_КОМПОНЕНТЫ_BOM.md` и `02_Наши_детали/ИНВЕНТАРЬ.md` для аппаратных/закупочных задач;
8. профильные файлы задачи.

Если контекст не прочитан, нельзя восстанавливать состояние по догадке.

Старые файлы `01_СТАТУС_ПРОЕКТА.md`, `02_СЛЕДУЮЩИЙ_ШАГ.md`, `03_СОСТОЯНИЕ_ПРОЕКТА.yaml` временно сохраняются для совместимости и handoff, но при конфликте `STATUS.md` имеет приоритет.

## 2. Назначение репозитория

ARDU — единый инженерный контекст проекта круглой потолочной лампы со светомузыкой, микрофоном, обычным светом/ночником, эффектами, будильником-рассветом и управлением со смартфона.

Документация должна быть технически точной, компактной, структурированной и пригодной для физической сборки.

## 3. Иерархия истины

1. последнее явное решение владельца;
2. `STATUS.md`;
3. более поздняя запись `DECISIONS.md`;
4. актуальный профильный документ;
5. старые материалы и ранние схемы.

Факт, предположение и решение не смешивать.

## 4. Журнал решений

`DECISIONS.md` ведётся append-only по смыслу.

Если решение изменилось:

1. старому присвоить статус `ЗАМЕНЕНО`;
2. не удалять его;
3. добавить новое решение;
4. объяснить причину и последствия.

## 5. История действий

`HISTORY.md` — хронология реально выполненного: фотоинвентаризация, измерения, прошивки, пайка, тесты, покупки, изменение схемы.

Не записывать планы как выполненные действия.

## 6. Источники

`SOURCES.md` хранит ссылки, исходные проекты, пользовательские фото/файлы, даташиты и результаты фактических измерений.

При идентификации конкретной детали приоритет имеет маркировка нашего экземпляра и измерение, а не типовое описание похожего товара.

## 7. Инвентаризация и закупки

Полный склад: `02_Наши_детали/ИНВЕНТАРЬ.md`.

Канонический перечень деталей проекта и закупок: `02_КОМПОНЕНТЫ_BOM.md`.

Главное правило текущей фазы:

`сначала инвентаризация → затем совместимость → затем архитектура/питание → только потом закупка`.

Не рекомендовать купить компонент, пока не проверено, нет ли функционального аналога среди уже имеющегося.

Для каждой детали фиксировать:

- точную маркировку;
- количество;
- источник идентификации;
- напряжение;
- ток/мощность, если важно;
- интерфейс и логические уровни;
- назначение;
- статус `основа / стенд / резерв / проверить / не нужен`;
- требуемые физические проверки.

Если одно устройство сфотографировано несколько раз, не считать фотографии отдельными экземплярами.

## 8. Текущая рабочая архитектура

До отдельного пересмотра:

`мобильное приложение → Wi‑Fi → ESP8266 → UART → Arduino Nano → MAX9814 / DS3231 / WS2812B`.

Nano — свет, звук, RTC, эффекты и машина состояний.

ESP8266 — сетевой шлюз.

HC-05 — временный резервный Bluetooth-канал.

Новый ESP32 не покупать без отдельного решения владельца.

## 9. Электрическая безопасность и подтверждение схемы

Требуют явной проверки до подключения:

- питание ESP8266;
- логические уровни Nano 5 В ↔ ESP8266 3,3 В;
- допустимый ток БП и проводов WS2812B;
- полярность питания;
- напряжение электролитических конденсаторов;
- фактическая распиновка модулей.

Не подавать 5 В на 3,3-вольтовый вход ESP8266.

Не считать типовой номинал модуля подтвержденным, если маркировка нашего экземпляра не читается.

## 10. Как объяснять физические подключения владельцу

При любом практическом объяснении проводки, компонентов и макетного стенда нельзя ограничиваться фразами вроде «поставить рядом», «подключить к питанию» или «добавить конденсатор».

Сначала прямо назвать **электрический тип соединения**: `параллельно`, `последовательно`, `напрямую`, `через резистор/делитель` и т. п. Если компонент физически должен находиться близко к другому, отдельно пояснить, что это требование размещения, а не иной тип электрического соединения.

Затем показать простую ASCII-схему с конкретными выводами. Предпочтительный формат:

```text
3.3V ───────► VCC ESP
  │
  └── (+) 100 мкФ (-) ──┐
                         │
GND ─────────────────────┴──► GND ESP
```

После схемы коротко написать словами: «конденсатор подключён параллельно; `+` к 3,3 В, `−` к GND; последовательно в провод питания его не ставить».

Для каждого практического подключения по возможности соблюдать порядок:

1. что с чем соединяется и каким типом соединения;
2. ASCII-схема;
3. точные контакты `источник → назначение`;
4. полярность, если она есть;
5. что категорически не соединять;
6. только после этого — зачем это нужно и техническое объяснение.

Если используются слова `рядом`, `около`, `ближе`, обязательно разделять два понятия: **электрически как подключено** и **физически где размещено**.

### Уровень объяснения: для начинающего

По умолчанию считать, что владелец может не знать компьютерный или электронный жаргон. Нельзя давать следующий шаг через необъяснённый термин.

Для каждого нового термина сразу писать простыми словами, что он означает. Например: `COM-порт` — это имя, которое компьютер присваивает подключённой плате, например `COM3` или `COM5`.

Инструкции давать как последовательность конкретных действий: **куда нажать → что выбрать → что должно появиться → что считать нормальным результатом**.

Не писать только «проверь порт», «открой монитор», «сделай reset», «подключи UART» и т. п. Сначала расшифровать термин и указать точное действие. Если используется сокращение (`UART`, `RX`, `TX`, `GND`, `VCC`), при первом появлении в текущем практическом эпизоде кратко объяснить его смысл.

Если можно сказать проще без потери точности, выбирать простую формулировку. Один практический шаг — одно действие или одна небольшая группа неразрывно связанных действий; не выдавать длинную цепочку вперёд, если владелец просит идти по одному шагу.

### Точность ссылок на диагностические значения

Если команда возвращает несколько полей, всегда указывать **имя конкретного поля**, которое сравнивается или считается нормой.

Например, для строки `ADC AVG=249 MIN=243 MAX=256 P2P=13` писать:
- `AVG около 240–260`;
- `MIN не у нижнего rail`;
- `MAX не у верхнего rail`;
- `P2P = ...`.

Нельзя писать расплывчато `ADC около 250`, `ADC низкий` или `ADC = 10`, если фактически речь идёт только об `AVG`. То же правило применять к `BANDS`, `STATUS`, `CALF`, напряжениям и другим многопараметрическим диагностическим строкам.

Это постоянное правило коммуникации проекта ARDU.

## 11. Работа с кодом

- Разделять транспорт команд и бизнес-логику.
- Смысл существующих команд не менять только из-за перехода Bluetooth → Wi‑Fi.
- Для Nano учитывать SRAM/Flash ATmega328P.
- Избегать бесконтрольных `String` и блокирующих задержек в рабочем контуре.
- Пины, число LED и электрические ограничения держать в централизованной конфигурации.
- AVR-специфичный FHT/ADC-код не считать автоматически переносимым на ESP8266.
- Сторонний код AlexGyver использовать с фиксацией источника и MIT License.
- Если скетч уже передан владельцу/начал тестироваться и затем исправляется код, обязательно повышать явную ревизию `R1→R2→R3`; не выдавать исправленный код под тем же неверсированным именем.
- Mode ID и firmware revision разделять: например `M05` остаётся ID режима, а реализация имеет `REV=2`.
- Для ревизионного скетча использовать версионированный путь/имя и печатать ревизию в startup/STATUS.

## 12. Минимальная верификация прошивки

1. компиляция для точной платы;
2. контроль использования памяти;
3. Serial/UART тест без ленты;
4. тест малого числа LED с ограниченной яркостью;
5. тест микрофона и калибровки;
6. только затем совместный тест Wi‑Fi + аудио + лента.

## 13. Обязательная синхронизация

После существенной работы до завершения ответа проверить необходимость обновления:

- `STATUS.md`;
- `DECISIONS.md`;
- `HISTORY.md`;
- `SOURCES.md`;
- `02_КОМПОНЕНТЫ_BOM.md`;
- `02_Наши_детали/ИНВЕНТАРЬ.md`.

Если изменился следующий практический шаг, синхронизировать также:

- `01_СТАТУС_ПРОЕКТА.md`;
- `02_СЛЕДУЮЩИЙ_ШАГ.md`;
- `03_СОСТОЯНИЕ_ПРОЕКТА.yaml`.

Нельзя писать владельцу, что информация «зафиксирована», если запись в репозиторий фактически не выполнена при доступной записи.
