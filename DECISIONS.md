# Журнал решений ARDU

Правило: файл append-only по смыслу. Если решение меняется, старое не удаляется — его статус меняется на `ЗАМЕНЕНО`, ниже добавляется новое решение с причиной.

---

## D-001 — отдельный репозиторий ARDU

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** весь проект лампы ведётся в `dronrome1245/ARDU` как едином инженерном контексте.

**Причина:** проект должен быть воспроизводимым между чатами и разными нейросетями.

---

## D-002 — основной источник звука: MAX9814 внутри лампы

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** базовый источник звука — микрофонный модуль MAX9814, который слышит музыку в помещении.

**Причина:** пользователь выбрал микрофонный вариант вместо AUX.

---

## D-003 — целевое управление: Wi‑Fi через приложение

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** конечное управление выполняется по Wi‑Fi через мобильное приложение. HC-05 сохраняется как резерв для отладки.

**Причина:** пользователь предпочёл Wi‑Fi; имеющаяся ESP8266 поддерживает Wi‑Fi, но не Bluetooth.

---

## D-004 — рабочая архитектура Nano + ESP8266

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ, ДО ПРОВЕРКИ СТЕНДОМ

**Решение:** Arduino Nano выполняет свет, звук, RTC и эффекты; ESP8266 работает Wi‑Fi-шлюзом; связь — UART.

**Причина:** не покупать ESP32, повторно использовать старый AVR-код и уже имеющиеся платы.

**Ограничение:** архитектура может быть упрощена только после стендовой проверки и отдельного решения.

---

## D-005 — сначала полная инвентаризация, затем покупки

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** не формировать окончательный список закупки до фиксации всего имеющегося железа и проверки совместимости.

**Причина:** у владельца много компонентов, часть обязательных деталей может уже быть в наличии.

**Последствие:** каждый новый фото-набор сначала попадает в инвентарь; статус `ДОКУПИТЬ` появляется только после технического обоснования.

---

## D-006 — ColorMusic AlexGyver используется как база, а не как неизменяемый проект

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** режимы и алгоритмы ColorMusic используются как исходная техническая база и адаптируются под микрофон, круглую лампу и сетевое управление.

**Ограничение:** при заимствовании исходного кода сохранять уведомление MIT License и фиксировать источник.

---

## D-007 — существующий протокол команд сохраняет семантику

**Дата:** 2026-09-05  
**Статус:** ЗАМЕНЕНО 2026-09-06 решением D-010

**Было:** переход Bluetooth → Wi‑Fi не должен сам по себе менять смысл старых команд приложения (`L1`, `M1`, `MM:n`, `CAL` и т. п.).

**Причина замены:** владелец решил писать мобильное приложение заново. Сохраняются функциональные режимы, но старый сетевой/командный формат больше не является обязательным интерфейсом совместимости.

---

## D-008 — обнаруженный YP-8 сначала проверяем, новый стабилизатор 3,3 В пока не покупаем

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ ДО ИЗМЕРЕНИЙ

**Решение:** модуль YP-8 на AMS1117-3.3 рассматривается как источник 3,3 В для ESP8266.

**Обязательная проверка:** измерить VOUT при 5 В на VIN; затем проверить просадку/нагрев под активной Wi‑Fi нагрузкой. До этого ESP8266 не подключать.

---

## D-009 — LCD, W5500, HC-SR04 и реле не входят в базовую архитектуру лампы

**Дата:** 2026-09-05  
**Статус:** ДЕЙСТВУЕТ

**Решение:** эти детали учитываются в общем инвентаре, но не считаются обязательными для ARDU.

**Исключение:** LCD 16×2 + PCF8574 допускается как временный диагностический интерфейс стенда.

---

## D-010 — мобильное приложение пишется заново

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** новый мобильный клиент проектируется заново под Wi‑Fi. Старый Bluetooth-интерфейс не ограничивает сетевой API.

**Сохраняется:** набор пользовательских режимов светомузыки/будильника как функциональная база; окончательный перечень режимов обсуждается отдельно.

---

## D-011 — круглые светильники больше не являются основным белым светом

**Дата:** 2026-09-06  
**Статус:** ЗАМЕНЕНО D-058 (2026-09-27)

**Решение:** два старых круглых корпуса используются только для WS2812B — светомузыка, декоративные эффекты и световой будильник. Основной белый свет детской обеспечивают отдельные точечные светильники на первой клавише.

**Следствие:** штатные белые LED-модули/драйверы круглых светильников не восстанавливаются и из приложения не управляются.

---

## D-012 — вторая клавиша является полным силовым отключением ARDU

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** вторая клавиша подаёт/снимает 230 В с общего БП ARDU целиком.

**Следствие:** световой будильник работает только если эта клавиша оставлена включённой на ночь. При штатной эксплуатации `OFF` задаётся программно, а клавиша используется как мастер-выключатель/сервисное отключение.

---

## D-013 — два светильника управляются одним контроллером синхронно

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** один Nano, один ESP8266, один MAX9814 и один DS3231 обслуживают оба круглых корпуса. Каждый WS2812B-контур получает отдельный DATA-выход Nano, но обе ленты отображают синхронный кадр.

**Причина:** меньше железа, единое состояние и отказ DATA одного кольца не должен обрывать второе кольцо.

---

## D-014 — Wi‑Fi: Station как основной режим, SoftAP как резерв настройки

**Дата:** 2026-09-06  
**Статус:** ЗАМЕНЕНО D-057 (2026-09-27)

**Решение:** для ежедневной работы ESP8266 подключается к домашнему Wi‑Fi (Station). Если сеть недоступна или требуется первичная настройка, ESP поднимает собственную SoftAP.

**Сетевой API первой версии:** локальный HTTP без облака. Для первой реализации приложение может хранить адрес устройства; автообнаружение можно добавить позже.

**Причина:** ежедневное управление не требует переключать Wi‑Fi телефона на отдельную сеть, а резервная SoftAP сохраняет доступ при смене роутера/пароля.

---

## D-015 — конкретная белая плата ESP8266 питается только 3,3 В

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** внешний `VCC` белой переходной платы ESP8266 считать 3,3-вольтовым. 5 В на этот контакт не подавать.

**Основание:** на фото платы присутствуют `103 / 0 / 103`; найденная документация на этот White Adapter описывает средний `0 Ω` как прямую перемычку VCC→Module-VCC при отсутствующем стабилизаторе. На нашем экземпляре дополнительный регулятор не установлен.

---

## D-017 — DS3231 с CR2032: зарядную цепь отключить

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** на нашем DS3231-модуле перед штатным питанием удалить/выпаять резистор `201` в цепи подзаряда батареи; CR2032 оставить как резервный первичный элемент.

**Основание:** на фото видны характерные стеклянный диод и `201`, соответствующие зарядной цепи распространённого ZS-042-подобного модуля. CR2032 является первичной, а не перезаряжаемой литиевой батареей.

## D-018 — целевая геометрия двух колец и лимит мощности

**Дата:** 2026-09-06  
**Статус:** ЗАМЕНЕНО D-064 (2026-09-27)

**Решение:** плотность фактической ленты ≈60 LED/м. Для кантика 71,5 см проектная цель — 43 LED на корпус, всего 86 LED.

**Питание:** оставить S-30-5 5 В 6 А, но в прошивке ограничить суммарный ток лент ориентировочно до 4,5 А. По D-058 постоянный белый L01 теперь является штатным режимом, но значение яркости должно автоматически оставаться в пределах программного лимита тока; «сырой» белый 100% без ограничения не допускается.

**Проверка:** окончательное число LED подтвердить физической укладкой до пайки.

## D-021 — фактический старый протокол отделён от нового протокола ARDU

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** символы `!`, `0`, `1…9`, `$`, `<`, `>`, `+`, `-`, `#`, `%`, `?`, `@` и др., найденные в `.aia`, считаются историческим Bluetooth-протоколом LumpV3.1. Проектные команды вида `L1`, `MM:n`, `MP1:n` не считать старым протоколом.

**Новый контракт:** телефон ↔ ESP8266 = локальный HTTP API; ESP8266 ↔ Nano = отдельный компактный UART-протокол.

## D-022 — функциональные разделы нового приложения

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** новое приложение имеет четыре рабочих раздела: `Светомузыка`, `Фон`, `Ночник`, `Будильник`, плюс общие настройки/диагностика.

**Причина:** это сохраняет полезную функциональную модель старого приложения, но убирает Bluetooth-архитектуру и неиспользуемый обычный белый свет.

## D-023 — режим ColorMusic №7 переносится в фоновые эффекты

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** `Постоянный цвет`, `Плавная смена цвета`, `Бегущая радуга` не считать музыкальными режимами ARDU. Они получают стабильные ID `F01–F03` в разделе `Фон`.

**Причина:** эти эффекты не зависят от звука и логически не относятся к светомузыке.

## D-024 — Kelvin не использовать как основную модель цвета WS2812B

**Дата:** 2026-09-06  
**Статус:** ДЕЙСТВУЕТ

**Решение:** старый параметр 1800–6600 K не переносится буквально. Для ночника и рассвета использовать цвет/HUE, насыщенность и яркость; для рассвета — начальный и конечный цвет.

**Причина:** WS2812B является RGB-лентой, а не CCT-лентой с отдельными белыми каналами.

## D-025 — стробоскоп только ручной дополнительный режим

**Дата:** 2026-09-06  
**Статус:** ЗАМЕНЕНО D-062 (2026-09-27) ДО УТОЧНЕНИЯ ПРЕДЕЛА ЧАСТОТЫ

**Решение:** M06 сохраняется для совместимости с исходной функциональностью ColorMusic, но не запускается автоматически, не используется в ночнике/будильнике и требует отдельного программного ограничения частоты до финальной реализации.

## D-026 — реализация прошивки по проверяемым слоям

**Дата:** 2026-09-06  
**Статус:** ЧАСТИЧНО ЗАМЕНЕНО 2026-09-20 решением D-033

**Решение:** не переносить весь ColorMusic одним шагом. Порядок: Nano → одно кольцо/F01 → два кольца → UART → MAX9814 → M01 → FHT/частотные режимы → фон → RTC/рассвет → ночник → стабилизация.

**Причина:** питание, Wi‑Fi, FHT и два кольца должны отлаживаться раздельно, чтобы ошибки имели понятный источник.

## D-027 — разделить согласование рабочего UART и programmer UART Nano

**Дата:** 2026-09-20  
**Статус:** ЗАМЕНЕНО 2026-09-20 решением D-028

**Решение:** не использовать одну и ту же расчётную модель делителя для двух разных путей:

1. рабочий `ATmega328P D1/TX → ESP RX` — отдельное внешнее согласование 5 В→3,3 В;
2. прошивочный `USB-UART Nano → D0/RX → ESP RX` — учитывать штатный последовательный резистор `1 кОм` Nano между USB-UART и D0.

**Причина:** первоначальная programmer-схема `1,5 кОм / 3,0 кОм` не учитывала штатный 1 кОм и могла увеличить выходное сопротивление/ухудшить UART-фронты. Ошибки esptool `C100/0107` требуют перепроверки programmer-path.

## D-028 — programmer UART рассчитывать только по фактической обвязке нашей Nano

**Дата:** 2026-09-20  
**Статус:** ДЕЙСТВУЕТ

**Решение:** для пути `USB-UART Nano → D0/RX0 → ESP RX` не предполагать штатный `1 кОм` по типовой схеме. Сначала определить реальный последовательный элемент на нашем экземпляре измерением.

**Основание:** на новых крупным фото рядом с USB-UART видны два `151` (=150 Ом), а `102` (=1 кОм) находятся у индикаторов. Фактические измерения внешнего делителя дали `D0 ≈ 4,95 В`, `ESP RX ≈ 3,36 В`, что также не подтверждает дополнительный 1 кОм перед D0.

**Не меняется:** рабочий путь `ATmega D1/TX → ESP RX` рассматривается отдельно и по-прежнему требует согласования уровня 5 В→3,3 В.


---

## D-029 — низкоомный programmer-divider для Nano→ESP

**Дата:** 2026-09-20  
**Статус:** ЗАМЕНЕНО 2026-09-20 решением D-030

**Решение:** для прошивки ESP8266 через Nano USB↔UART вместо внешнего делителя 1,5 кОм / 3,0 кОм попробовать более низкоомный делитель: верхнее плечо `750 Ом` (два 1,5 кОм параллельно), нижнее `1,5 кОм`.

**Причина:** без внешнего делителя upload продвинулся с ~15% до 30%, что указывает на влияние высокого выходного сопротивления прежней схемы; прямой 5-вольтовый UART на ESP RX небезопасен.

**Проверка:** перед подключением ESP измерить HIGH на средней точке; целевой уровень около 3,0–3,4 В.

## D-030 — успешная диагностическая прошивка не узаконивает прямой 5 В UART

**Дата:** 2026-09-20  
**Статус:** ДЕЙСТВУЕТ

**Решение:** считать возможность прошивки ESP8266 через имеющийся Nano подтверждённой, но прямое соединение `Nano D0 (~5 В) → ESP RX` не использовать как постоянную или повторяемую штатную схему. Локальный `100 µF 10 V` у ESP оставить в стендовой схеме питания. Безопасное programmer-level-shift определить отдельно.

**Основание:** полная запись flash и `Hash of data verified` получены при прямом D0→RX и 100 µF, однако два изменения были внесены одновременно, поэтому нельзя приписать успех только одному фактору. 5-вольтовый логический уровень превышает штатное 3,3-вольтовое питание входа ESP.


---

## D-031 — programmer-divider ESP временно отложить, продолжить по слоям FW

**Дата:** 2026-09-20  
**Статус:** ДЕЙСТВУЕТ

**Решение владельца:** временно прекратить подбор делителя именно для процедуры прошивки ESP8266 и продолжить реализацию ARDU по утверждённому порядку прошивки.

**Граница решения:** это не разрешает прямые ~5 В на ESP RX как штатную электрическую схему. Безопасный programmer-level-shift остаётся открытой задачей и должен быть закрыт до финальной/регулярной процедуры прошивки.

**Следующий слой:** `FW-0` Nano → затем `FW-1` одно кольцо/F01 → `FW-2` два кольца → `FW-3` рабочий UART ESP8266↔Nano.


---

## D-032 — схемы AlexGyver/ColorMusic использовать как базовую аппаратную опору

**Дата:** 2026-09-20  
**Статус:** ДЕЙСТВУЕТ

**Решение владельца:** при наличии опубликованной и проверенной автором схемы ColorMusic/AlexGyver придерживаться её как базовой для соответствующего узла. Отклонения допускаются только если наша архитектура/компоненты требуют этого и причина зафиксирована.

**Для WS2812B:**
- электролит `1000–2200 µF` параллельно питанию ленты у входа;
- DATA через последовательный резистор `200–500 Ом` (целевой 330 Ом);
- общая GND Arduino и ленты обязательна;
- ленту питать от отдельного 5-вольтового БП, не через Arduino.

**Уточнение:** 1000 µF и DATA-резистор не взаимозаменяемы. Предыдущий временный вариант `1,5 кОм` в DATA для FW-1 отменён.


---

## D-033 — второе кольцо физически тестировать после полной настройки первого

**Дата:** 2026-09-20  
**Статус:** ДЕЙСТВУЕТ

**Решение владельца:** не выполнять сейчас отдельный физический этап второго кольца. `D7` зарезервирован как зеркальный DATA-канал: второе кольцо должно получать тот же кадр, что и первое на `D6`, без отдельной пользовательской логики.

**Порядок:** сначала довести одно кольцо до устойчивой полной настройки и интеграции остальных подсистем; затем подключить второй канал и проверить зеркальную работу/питание двух колец.

**Причина:** не добавлять второй физический источник неизвестностей, пока базовый однокольцевой тракт ещё развивается.


---

## D-034 — для FHT использовать AvrFHT вместо старой вложенной FHT ColorMusic

**Дата:** 2026-09-20  
**Статус:** ЗАМЕНЕНО D-036

**Решение:** на Nano ATmega328P использовать библиотеку `AvrFHT` (KobaProduction) как современную AVR-совместимую реализацию исходной ArduinoFHT. Алгоритмические диапазоны и логика ColorMusic сохраняются, но API адаптируется к AvrFHT.

## D-037 — аудиовход ARDU повторяет двухвходовую логику поздней ColorMusic

**Дата:** 2026-09-21  
**Статус:** ЗАМЕНЕНО D-040

**Решение владельца:** придерживаться поздней официальной AlexGyver ColorMusic как основной базы музыкального тракта.

Для финального музыкального входа Nano принять ту же функциональную схему, что в `colorMusic_v2.10`:
- `A2` — основной mono/VU вход (`SOUND_R`);
- `A3` — отдельный вход для FHT/частотных режимов (`SOUND_R_FREQ`, через конденсатор);
- `A1` не нужен, так как ARDU mono;
- `A0` больше не является финальным микрофонным входом; его текущие тесты считаются диагностическим стендом.

Причина выбора A2/A3, а не перенос логики на A0/A3: минимизировать перекомпоновку исходного ColorMusic v2.10 и сохранить соответствие оригинальным именам/схеме. Точный узел конденсаторов/AREF собрать по официальной микрофонной схеме до перехода к M03/M04.

## D-038 — стендовая обвязка A2/A3 для перехода на ColorMusic v2.10

**Дата:** 2026-09-21  
**Статус:** ЗАМЕНЕНО D-039

Для первого воспроизводимого стенда A2/A3 принять:
- C1 между MAX9814 Out и A2: 1 µF электролит, рабочее напряжение ≥6,3 V; плюс к Out, минус к A2. Допустимый исходный диапазон ColorMusic — 1–100 µF.
- A2 к GND через 9,4 kΩ = два имеющихся 4,7 kΩ последовательно; это безопасная обратимая замена «около 10 kΩ».
- A2 к A3 через неполярный 10 nF, маркировка 103.
- MAX9814 Gain→Vdd (40 dB), AR floating.
- Для тестового скетча AREF = INTERNAL 1,1 V, как в поздней ColorMusic при POTENT=0.

A0 не используется в финальном аудиотракте. Точный результат схемы подтвердить командами ADC2/ADC3/CALF/FREQ и regression-тестом 2/5/8 кГц.

## D-039 — A2/A3 собирать без pull-down, строго по официальной схеме ColorMusic

**Дата:** 2026-09-22  
**Статус:** ЗАМЕНЕНО D-040

После сверки с предоставленной владельцем официальной схемой AlexGyver исправлена ошибка D-038.

Точная сигнальная цепь:
- MAX9814 Out → электролит C1 1–100 µF (≥6,3 V) → Nano A2;
- Nano A2 → конденсатор 103 / 10 nF → Nano A3;

Цепочка 2×4,7 kΩ (=9,4 kΩ) A2→GND была предложена ИИ как проектная добавка, но отсутствует на официальной схеме и отменена.

## D-040 — MAX9814 single-input на A0 с программным DC subtraction

**Дата:** 2026-09-22  
**Статус:** ДЕЙСТВУЕТ

- `Gain → Vdd` = 40 dB;
- `AR` оставить неподключённым;
- `analogReference(DEFAULT)` (~5 V);
- DC offset измерять программно и вычитать перед FHT.

Набор и визуальная логика режимов поздней ColorMusic сохраняются. Меняется только аналоговый frontend: M01/M02 получают уровень из того же A0, а M03/M04/M05/M08/M09 используют FHT того же A0 после программного DC subtraction.

## D-042 — исправления тестируемой прошивки получают новую ревизию

**Дата:** 2026-09-25

## D-043 — M05 calibration must reject invalid MAX9814 DC

**Дата:** 2026-09-26  
**Статус:** ДЕЙСТВУЕТ

**Решение:** для текущего MAX9814/A0 frontend M05 считать DC валидным только в широком защитном диапазоне `120..400` ADC counts. Значения вне диапазона не использовать для FHT/noise calibration.

**Поведение:** `CALF` при invalid DC завершается `ERR CALF_BAD_DC`, не выставляет `CAL=YES`; STATUS показывает `DC_OK=YES/NO`.

**Причина:** M05 R2 после аппаратного reset/сбоя показал `DC=1000` и мог оставаться в состоянии `CAL=YES`, что маскировало неисправный аналоговый вход.

**Граница:** диапазон является safety guard для текущего подтверждённого MAX9814/A0 тракта, а не универсальной спецификацией всех возможных микрофонов.

## D-055 — NIGHT R2 schedule semantics

**Дата:** 2026-09-26  
**Статус:** ДЕЙСТВУЕТ

**Решение:** базовый ночник FW-9 включает автоматическое расписание DS3231.

Правила:
- schedule по умолчанию выключен;
- default сохранённого интервала: `22:00 → 07:00`;
- interval = `[ON, OFF)`: в минуту ON ночник активен, в минуту OFF уже выключен;
- если ON < OFF, используется дневной интервал `ON ≤ now < OFF`;
- если ON > OFF, интервал проходит через полночь: `now ≥ ON || now < OFF`;
- одинаковые ON/OFF запрещены как неоднозначные;
- `SCHEDULE ON` немедленно вычисляет POWER по текущему DS3231;
- manual `ON` или `OFF` отключает schedule и становится явным пользовательским override;
- изменение HUE/SAT/BRIGHT не отключает schedule;
- при включённом schedule и невалидном RTC effective POWER = OFF;
- автоматические переходы не записывают EEPROM.

**Причина:** поведение должно быть детерминированным после reset и не должно неожиданно отменять ручную команду пользователя.

## D-060 — настройки всех режимов сохраняются на Nano

**Дата:** 2026-09-27  
**Статус:** ДЕЙСТВУЕТ

**Решение владельца:** параметры каждого пользовательского режима должны сохраняться энергонезависимо и восстанавливаться после отключения питания. Мобильное приложение также должно сохранять/показывать настройки всех режимов.

Архитектура v1:

- Nano — источник истины по настройкам;
- отдельные настройки каждого режима сохраняются независимо;

**Важно:** текущие отдельные тестовые скетчи, включая M02 R1, не обязаны реализовывать всю persistence-архитектуру. Она является обязательным критерием единой полной Nano-прошивки.

## D-061 — M06 R1 strobe firmware limits

**Дата:** 2026-09-27  
**Статус:** ЗАМЕНЕНО D-062 (2026-09-27)

**Решение:** первый аппаратный M06 реализовать как только ручной режим с ограничениями непосредственно в Nano:

- после boot M06 = OFF;
- не запускать автоматически из music/ambient/night/alarm;

## D-063 — L01 поддерживает Kelvin, произвольный цвет и startup profile

## D-068 — clap calibration запускается из приложения и учитывает нескольких пользователей

**Дата:** 2026-09-27  
**Статус:** ДЕЙСТВУЕТ

**Решение владельца:** хлопковый выключатель не должен иметь один жёстко заданный threshold, настроенный по хлопку взрослого. Калибровка должна запускаться из мобильного приложения и учитывать пользователей разного возраста/силы хлопка.

Архитектура:

- один общий detector для устройства;
- приложение запускает guided calibration;
- Nano сначала измеряет quiet derivative baseline;
- затем приложение предлагает нескольким пользователям выполнить серии double-clap;
- Nano собирает clap-strength samples;
- итоговый threshold выбирается по нижней устойчивой части распределения хлопков, чтобы учитывать более слабых пользователей;
- suggested threshold сначала применяется в RAM и тестируется;
- только после подтверждения пользователя сохраняется в EEPROM;
- `CANCEL` возвращает предыдущую сохранённую калибровку;
- threshold переживает reset и power cycle.

Для семьи из трёх пользователей базовый UX: 3 успешных double-clap sample на пользователя = 9 пар.

Тестовая реализация: `nano_clap_gyver_r3_cal`.

## D-070 — FW-10 reset priority: active Dawn recovery > cold L01; stale HOLD < cold L01

**Дата:** 2026-09-27  
**Статус:** ДЕЙСТВУЕТ ДЛЯ FW-10 CORE R1

При интеграции D-053 Dawn recovery и D-058 cold-power L01 используется приоритет:

1. если после reset/power interruption сохранён `DAWN RUNNING` и по DS3231 он всё ещё реально не завершён — восстановить активный Dawn;

## D-073 — пользовательский L01 не использует raw Developer endpoint

**Дата:** 2026-09-30  
**Статус:** ЗАМЕНЕНО D-074

Первый пользовательский слой L01 после закрытия Android transport R1 реализуется через semantic HTTP API ESP, а не через `/api/dev/nano`.

Порядок первой итерации:
1. `GET /api/light/status` читает фактический `STATUS` + `LIGHT STATUS` Nano и формирует пользовательское состояние;
2. `POST /api/light/settings` в HTTP_BRIDGE_R2 принимает только атомарное поле `enabled` и переводит его в `LIGHT ON/OFF`;
3. неподдерживаемые поля отклоняются явно, а не игнорируются;
4. расширение brightness/Kelvin/RGB/persistence выполняется следующими малыми итерациями после аппаратного ON/OFF pass;
5. raw `/api/dev/nano` остаётся сервисным Developer Mode.

**Причина:** сохранить Nano источником истины, не связывать обычный UI с внутренним UART-протоколом и тестировать интеграцию маленькими обратимыми слоями.

## D-074 — не перепрошивать компактно спаянный ESP для каждой app-итерации

**Дата:** 2026-09-30  
**Статус:** ДЕЙСТВУЕТ  
**ЗАМЕНЯЕТ:** D-073 как обязательный порядок ближайших app-итераций.

**Решение владельца:** рабочий ESP/Nano стенд уже компактно спаян; не выполнять повторную физическую перепрошивку ESP ради каждого следующего экрана/параметра приложения.

До отдельного пакетного ESP update:
1. физический ESP остаётся на hardware-tested `HTTP_BRIDGE_R1`;
2. обычный Android UI может использовать `/api/dev/nano` внутри transport/repository layer как временный compatibility adapter;
3. raw Nano-команды, IP и UART не показываются обычному пользователю;
4. после каждой команды приложение перечитывает состояние Nano, который остаётся источником истины;
5. HTTP_BRIDGE_R2 и последующие semantic ESP endpoints разрабатываются/накапливаются в репозитории, но прошиваются пакетно, когда это оправдывает вмешательство в монтаж.

## D-078 — финальная физическая топология двух потолочных корпусов

**Дата:** 2026-10-01  
**Статус:** ДЕЙСТВУЕТ

Подтверждённые условия:
- корпуса находятся примерно в 2 м друг от друга;
- существующая линия к корпусам — 2×2,5 мм² от одного выключателя;
- скрытая настенная часть проводки недоступна;
- у корпуса A доступна потолочная точка бывшей люстры;
- владелец может провести новую low-voltage трассу за потолком к корпусу B.

**Решение:**
1. S-30-5 и общий контроллерный узел Nano/ESP/RTC/MAX9814 размещать у корпуса A.
2. Ring A питается локально и получает DATA D6.
3. Ring B получает DATA D7 и отдельную новую ~2 м low-voltage ветвь.
4. Ветка Ring B должна содержать +5V, GND и DATA; DATA вести с близким reference GND.
5. Существующую 230-V линию не использовать как DATA/signal path.
6. Для +5V/GND Ring B ориентироваться на медь около 1,5 мм² или больше, затем подтвердить реальное падение напряжения под двухкольцевой нагрузкой.
7. Current limit подбирать после load test через service setting, без новой прошивки.
8. До монтажа обязательно проверить конкретный S-30-5 по маркировке входных клемм и требованию PE/FG; наличие защитного PE при двухжильном вводе не предполагается автоматически.

**Последнее явное решение владельца:** аккумулятор не должен быть постоянно подключён, но ARDU должна иметь возможность подключить внешний аккумуляторный блок 5 В при отключении сети, чтобы лампы продолжали работать.

**Решение:**
1. В финальной силовой архитектуре ARDU предусмотреть отдельный обслуживаемый вход `EXT 5V` у общего контроллерного/силового узла корпуса A.
2. `EXT 5V` питает **общую 5-вольтовую шину всей ARDU**: оба кольца WS2812B, Nano и низковольтные подсистемы через их штатные ветви. Не подавать ток ламп через USB-разъём Nano или через дорожки платы Nano.
3. Штатный Class II 230→5 V PSU и внешний 5 V источник **не соединять параллельно напрямую**. Для v1 предпочтителен простой ручной двухполюсный выбор источника `NORMAL / EXT 5V` с достаточным DC-токовым запасом; эквивалентная MOSFET ideal-diode развязка допустима позже, если появится реальная необходимость в автоматическом переключении.
4. Ветка `EXT 5V` получает отдельный предохранитель у входного разъёма; точный номинал выбрать после финального current-limit и сечения проводов.
5. При текущем подтверждённом software current limit `3000 mA` для лент резервный источник должен выдавать стабильные 5 В с практическим запасом на Nano/ESP/RTC/MAX9814; ориентир — **не менее 4 А continuous**, предпочтительно 5–6 А. Если использовать обычный 5 V / 3 A power bank, перед эксплуатацией требуется понизить LED current limit.
6. Встроенной зарядки аккумулятора в ARDU не делать. Внешний battery block считается самостоятельным защищённым источником 5 В со своим BMS/преобразователем.
7. Cold-start semantics не меняются: после выбора резервного источника и подачи 5 В Nano загружается штатно и включает L01. Базовый свет не должен зависеть от доступности Wi‑Fi/роутера.
8. Прошивки Nano/ESP, HTTP API v1 и numeric UART v1 этим решением не изменяются.
9. Hardware acceptance выполнить на этапе финального power/two-ring gate: проверить отсутствие backfeed между источниками, напряжение на дальней кольце, нагрев силовых контактов и устойчивый L01 на резервном 5 V источнике.

## D-097 — Station primary + protected SoftAP fallback

**Дата:** 2026-10-05  
**Статус:** ДЕЙСТВУЕТ / OWNER APPROVED  
**Заменяет:** сетевую часть D-057 `только домашний Wi-Fi / SoftAP не реализовывать`.

**Основание (актуализировано D-100):** возможность локального управления без домашнего роутера полезна сама по себе и сохраняется независимо от отказа от аккумуляторного резервного питания.

**Решение:**
1. Домашний Wi-Fi Station остаётся основным режимом.
2. Если ESP8266 не может подключиться к домашней сети при старте либо теряет Station в работе, включается защищённая SoftAP `ARDU-DIRECT`.
3. Адрес direct mode фиксирован: `192.168.4.1`.
4. SoftAP требует отдельный локальный пароль минимум 8 символов; пароль не коммитится.
5. При восстановлении домашнего Wi-Fi ESP возвращается в Station и выключает SoftAP.
6. HTTP API v1 и numeric UART v1 одинаковы в Station и direct mode; Nano не меняется.
7. OTA остаётся Station-only: direct mode предназначен для управления лампой, а не для сервисной прошивки.
8. Android client ищет сохранённый адрес и резервный `192.168.4.1`; отсутствие `wifi_connected=true` не считается ошибкой, если `/api/ping` получен напрямую от ARDU.
9. Источник 2026-10-05 реализован в ESP/Android; физический direct-mode smoke обязателен до финального потолочного монтажа.

## D-098 — v1 устанавливается без аккумулятора, но с готовым внешним USB-C PD reserve input

**Дата:** 2026-10-05  
**Статус:** ЗАМЕНЕНО D-100 / ОТМЕНЕНО ВЛАДЕЛЬЦЕМ 2026-10-07  
**Уточняет:** D-096.

**Последнее явное решение владельца:** первый законченный ARDU должен работать без аккумулятора, но после потолочного монтажа внешний аккумулятор должен подключаться без снятия лампы.

**Решение:**
1. Аккумулятор в ARDU не устанавливать и не заряжать.
2. До потолочного монтажа физически вывести на доступную часть корпуса A внешний разъём `BACKUP / USB-C PD`.
3. Резервный тракт внутри ARDU подготовить заранее: `USB-C PD input → PD trigger 15 V → входной fuse → 15→5 V DC/DC ≥5 A → source selector → common 5 V bus`.
4. 15 V на внешнем входе выбрано специально: при той же мощности ток в внешнем кабеле/разъёме ниже, чем у прямого 5 V/5–6 A входа.
5. Штатный Class II 5 V PSU и reserve 5 V output не параллелить напрямую. Для v1 оставить доступный ручной двухполюсный `NORMAL / BACKUP` selector, желательно break-before-make.
6. Резервный DC/DC питает общую 5-V шину ARDU, а не USB или силовые дорожки Nano.
7. Current limit Nano остаётся источником ограничения LED load; до two-ring power acceptance physical baseline = 3000 mA.
8. USB-C PD source должен поддерживать как минимум 15 V / 2 A; для запаса выбран класс 15 V / 3 A (45 W).
9. Финальный reserve hardware gate: 15 V PD negotiation, 5 V rail under load, отсутствие backfeed, нагрев converter/selector/connectors, дальнее кольцо, cold-start L01 и direct Wi-Fi.
10. Конкретный внешний аккумулятор — опциональная покупка после завершения лампы; базовый v1 считается законченным без него.

## D-099 — selectable ring profiles and automatic reserve source

**Дата:** 2026-10-05  
**Статус:** ЗАМЕНЕНО D-100 / ОТМЕНЕНО ВЛАДЕЛЬЦЕМ 2026-10-07  
**Уточняет/частично заменяет:** D-098 manual NORMAL/BACKUP selector.

**Последнее явное решение владельца:** будущий аккумулятор остаётся выбранного класса; добавить выбор кольца и для обычного, и для аварийного режима; ручной переключатель источника не нужен.

**Решение:**
1. В Nano хранить два независимых persistent-профиля вывода: `normal_ring` и `emergency_ring`.
2. Допустимые значения обоих профилей: `BOTH`, `A`, `B`.
3. Defaults: normal=`BOTH`, emergency=`A`.
4. Профиль применяется централизованно ко всем режимам света (L01/Music/Ambient/Night/Dawn), а не только к обычному свету.
5. Источник режима определяется по `D8 MAINS_SENSE`: HIGH = штатный PSU, LOW = резервное питание.
6. MAINS_SENSE hardware для финальной сборки: `MAIN_5V -> 1.5 kOhm -> D8`, `D8 -> 4.7 kOhm -> GND`. Оба номинала уже есть в инвентаре.
7. Автоматический выбор источника выполняет существующий relay module INV-051 (`SRD-05VDC-SL-C`) после отдельного contact/load test: COM → common +5V bus, NO → MAIN_5V, NC → BACKUP_5V. Катушка/driver питаются от MAIN_5V и должны удерживать NO при наличии сети.
8. При отсутствии аккумулятора резервная ветвь просто не питает NC; ARDU v1 остаётся полноценной сетевой лампой.
9. Выбор A/B/BOTH выполняется программно по независимым D6/D7. Неактивное кольцо получает black frame, но физически остаётся запитанным; отдельный high-side power cut не требуется для v1.
10. Общий software current limit учитывает число активных колец.
11. HTTP API: `/api/system/rings`; numeric UART: 121 read / 122 set.
12. Android Settings содержит отдельные `Обычный режим` и `Аварийный режим`, по три варианта `Оба / A / B`.
13. Будущий аккумулятор остаётся UGREEN Nexode 20000 mAh 100 W (SKU 25188) или эквивалент с 15 V / 3 A PD; в первую версию аккумулятор не покупать.
